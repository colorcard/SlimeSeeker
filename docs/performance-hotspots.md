# SlimeSeeker 性能热点分析基线

本文记录 2026-08-26 的初步 CPU 热点分析，作为后续优化前后的对照基线。数据只适合在相同
硬件、编译器和输入条件下比较，不应作为跨机器的绝对性能承诺。

## 测试环境与方法

- CPU：Apple M1 Max，10 核（8 性能核 + 2 能效核）
- 内存：32 GiB
- 系统：macOS 15.7.1，arm64
- 编译器：AppleClang 17
- 构建：CMake Release；额外构建 RelWithDebInfo 用于符号采样
- 采样器：macOS `sample`，1 ms 周期、5秒采样窗口
- 默认分析输入：seed `0`、range `30000`、threshold `45`、scalar、单线程

默认输入包含 36 亿个候选中心，端到端耗时约 10.8 秒，吞吐约 3.33 亿候选/秒。主线程
几乎全部等待 worker，说明默认高阈值下 CLI、进度回调和结果队列不是主要瓶颈。

## 默认高阈值热点

| 热点层 | 端到端占比 | 主要开销 |
|---|---:|---|
| 史莱姆位图生成 | 约 46–51% | chunk seed、LCG、写入 byte map |
| Java LCG 判定 | 约 33–37% | 48 位乘加、掩码、取模和 rejection 判断 |
| SAT 与候选预筛 | 约 49–53% | SAT 写入、每中心四次读取、阈值分支 |
| tile 分配与释放 | 约 1% | map/SAT/xterm scratch 的申请、清零与释放 |
| 结果队列与回调 | 接近 0% | threshold 45 的命中数量很少 |

高阈值下没有单一绝对瓶颈，而是“位图生成”与“SAT/候选扫描”大致各占一半。最大的单个
叶子热点是 `is_slime_from_chunk_seed()`，但即使完全消除 LCG 成本，按 Amdahl 定律计算，
默认负载的理论上限也约为 1.5 倍。

相关位置：

- `src/core/domain.cpp`：Java LCG 与 `nextInt(10)`
- `src/backends/scalar.cpp`：xterm/zbase 与位图生成
- `src/engine/search.cpp`：SAT 构建、包围盒预筛和20段精确计数

## LTO 对照实验

当前 Release 默认未启用跨过程优化。LCG 函数位于独立编译单元，数十亿次调用会产生调用
成本，并限制编译器跨函数优化。使用完全相同源码，仅打开
`CMAKE_INTERPROCEDURAL_OPTIMIZATION=ON` 后得到：

| 场景 | 普通 Release | LTO | 提升 |
|---|---:|---:|---:|
| 单线程，threshold 45 | 约 3.44 亿/s | 约 3.76 亿/s | 约 9.3% |
| 10线程，threshold 45 | 约 23.5 亿/s | 约 25.3 亿/s | 约 7.7% |

因此，启用经过平台检查的 IPO/LTO，或将内部 LCG 热函数内联，是当前证据最充分、实现风险
最低的第一优先级优化。正式启用前仍需在 MSVC、GCC、Clang 和静态/共享库构建中验证。

### P0 实施结果

P0 已完成以下调整：

1. Release/RelWithDebInfo 默认使用 `CheckIPOSupported` 探测并启用 IPO，可用
   `SLIMESEEKER_ENABLE_IPO=OFF` 构建对照版本；
2. 精确 LCG 热函数移入内部头文件并内联；arm64 反汇编确认 `%10` 热路径没有生成整数除法，
   二进制中也不再保留独立的 `is_slime_from_chunk_seed` 调用符号；
3. map、SAT 和 xterm 改为每 worker 一次分配、跨 tile 复用；
4. SAT 不再为每个 tile 整块清零，只重置首行与每行首列，其余位置由构建循环覆盖。

在相同源码、IPO 开/关的五轮中位数对照中，内联已经捕获了大部分单线程跨函数收益；IPO 对
单线程额外提升较小，对10线程仍有约8.6%的端到端收益。使用改动前同样开启 LTO 的二进制
交替运行，隔离 scratch 与清零策略的影响：

| 场景 | P0 前 LTO | P0 后 LTO | 提升 |
|---|---:|---:|---:|
| 单线程，threshold 45 | 约 3.72 亿/s | 约 3.98 亿/s | 约 6.8% |
| 10线程，threshold 45 | 约 27.2 亿/s | 约 29.8 亿/s | 约 9.6% |

相对本文最初记录的普通 Release 基线，当前默认构建代表值约提升16%（单线程）和31%
（10线程）。不同轮次会受温度、频率和系统调度影响，应优先使用交替运行的中位数评价。

低阈值路径也有改善，但圆环精确计数仍占主导：单线程 threshold 30/25/20/0 相比初始基线
约提升4%/7%/8%/4%，没有改变 P1 需要引入滑动圆环计数的结论。

## 线程扩展

测试输入为 seed `0`、range `15000`、threshold `45`、scalar，表中为三次运行的代表值：

| 线程数 | 吞吐 | 相对单线程 |
|---:|---:|---:|
| 1 | 约 3.43 亿/s | 1.00× |
| 2 | 约 6.79 亿/s | 1.98× |
| 4 | 约 13.28 亿/s | 3.87× |
| 6 | 约 19.55 亿/s | 5.70× |
| 8 | 约 22.39 亿/s | 6.53× |
| 10 | 约 22.7 亿/s | 约 6.6× |

1到6线程扩展良好，表明动态 tile 调度和原子领取不是主要瓶颈。8线程后收益明显下降，10线程
只比8线程快约1–4%，与 M1 Max 的8个性能核加2个能效核结构相符。10线程、36亿候选运行
测得 11.54 秒 user / 1.53 秒 wall，平均有效使用约7.5个CPU核心。

后续可研究按性能核选择默认线程数，但不建议优先重写调度器或增加更细粒度任务。

## 阈值敏感性与瓶颈转移

单线程、scalar、1600万候选实测：

| 阈值 | 吞吐 | 相对 threshold 45 |
|---:|---:|---:|
| 45 | 约 3.35 亿/s | 1.00× |
| 30 | 约 7119 万/s | 0.21× |
| 25 | 约 4100 万/s | 0.12× |
| 20 | 约 3243 万/s | 0.10× |
| 0 | 约 3408 万/s | 0.10× |

阈值降低后，大量候选通过17×17包围盒预筛，需要执行20段圆环精确计数。当前每个精确候选
需要 `20 × 4 = 80` 次 SAT 读取，瓶颈由 LCG/SAT 构建转移为：

1. 圆环精确查询的读取和地址计算；
2. 阈值附近不可预测的分支；
3. 大量结果写入 worker batch；
4. 有界队列与调用线程消费；
5. CLI 全量排序或 Top-K 维护。

因此不能用 threshold 45 的热点结论指导所有场景。后续基准必须至少覆盖“高阈值稀疏命中”
与“低阈值密集命中”两类负载。

## SIMD 后端现状

| 后端 | 单线程 | 10线程 |
|---|---:|---:|
| scalar | 约 3.43 亿/s | 约 22.7 亿/s |
| NEON | 约 3.43 亿/s | 约 20.3 亿/s |

当前 NEON 只批量生成每 tile 约512个 xterm，而每 tile 需要约262144次 LCG，优化覆盖面不足
0.2%。因此单线程基本持平，多线程反而慢约10%，`auto` 选择 scalar 是正确行为。

真正可能改变总耗时的 SIMD 方案必须覆盖完整 LCG、魔数取模和 lane rejection 回退。由于
AVX2/NEON 缺少直接适配此热路径的低成本64位向量乘法，应在 LTO、流水线融合之后再研究，
并以逐位对拍与端到端收益作为是否进入 `auto` 的门槛。

## 内存、tile 与次要开销

- 10线程、36亿候选最大常驻内存约16 MiB，无 swap 和磁盘 I/O，不属于容量型内存瓶颈。
- 每个满 tile 的 map 约256 KiB、SAT 约526 KiB、xterm 约4 KiB。
- 每 tile 处理496×496个中心，却生成512×512位图，位图重复计算比例约6.56%。
- 重叠只影响约一半的位图阶段，因此完全消除后的默认端到端理论收益约3%。
- 分配、释放和清零采样占比约1%；每 worker 复用 scratch 是低风险、小收益优化。

条带化或跨 tile 边缘复用会增加 worker 间依赖，不应在更高收益优化完成前优先实施。

## 优化路线

### P0：低风险、已有数据支持（已完成）

1. 已使用 `CheckIPOSupported` 为优化构建启用可选 IPO/LTO；当前已验证 AppleClang 和共享库，
   MSVC/GCC 由 CI 持续验证。
2. 已内联 LCG 热函数并检查 arm64 生成代码。
3. 已实现每 worker 的 map、SAT 和 xterm scratch 复用。

### P1：流水线和低阈值优化

1. 融合位图生成与 SAT 构建，避免 byte map 写入后立即重读。
2. 为低阈值增加滑动圆环计数：中心横移时只加入和移除每段边界，减少精确查询读取。
3. 分离高阈值预筛路径与低阈值密集路径，按阈值或实测通过率选择算法。
4. 密集命中时评估更大的结果批次、worker 局部 Top-K 或统计模式，降低主线程压力。

### P2：复杂专用优化

1. 实现覆盖完整 LCG 的 NEON/AVX2 多 lane 版本，并保留精确 rejection 冷路径。
2. 根据 CPU 拓扑与短基准选择默认线程数。
3. 评估条带扫描或边缘缓存，消除约6.56%的 tile 位图重叠。

## 后续优化的验收要求

每项性能修改必须同时满足：

1. scalar、专用后端与三个完整黄金种子逐位一致；
2. 普通 CTest、C ABI smoke 和 Sanitizer 通过；
3. 同机至少重复5次并报告中位数；
4. 同时报告单线程、多线程、高阈值和低阈值结果；
5. 不以增加默认内存无上限、截断结果或弱化 rejection 语义换取性能。
