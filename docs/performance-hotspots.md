# SlimeSeeker 性能热点与优化路线

本文记录 2026-08-26 在当前 CPU 与 CUDA 实现上的同机性能基线，并据此确定下一阶段的
优化顺序。结论只适用于本文所列硬件、编译器、构建配置和输入；吞吐用于同机回归，不是
跨平台性能承诺。

## 结论摘要

下一步应优先重构 **CUDA 资源生命周期与多 tile 异步流水线**，而不是继续微调 CUDA
kernel。高阈值 4 亿候选的两个 kernel 合计只占约 18.14 ms，但当前实现对 1681 个 tile
逐个执行、逐个 `cudaDeviceSynchronize()`，且每次搜索都初始化 runtime、申请设备与锁页
内存。冷启动和主机编排已经淹没 kernel 算力，原生 `sm_120` 带来的 kernel 加速也只能转化
为约 0--3% 的端到端收益。

CPU 优化必须按阈值分开处理：

- 高阈值主要由位图生成和滑动方框管线共同限制，完整 SIMD LCG 仍有价值，但不是全局 P0；
- 中阈值约八成指令花在 SAT 候选扫描和 20 段精确圆环查询，应优先研究相邻中心批处理、
  bit-packed map 与 `popcount`；
- 低阈值主要受 20 段滑动更新和密集结果交付限制，默认 1024 条批次会造成显著队列等待，
  需要同时优化计数和有界回传，不能通过丢弃结果制造虚假吞吐。

优先级因此确定为：

1. **P0：CUDA 常驻资源、多 tile 批处理和异步回传；**
2. **P1：低阈值 CPU 批量计数与结果交付；**
3. **P2：中阈值 SAT/圆环查询的数据布局与向量化；**
4. **P3：高阈值完整 CPU SIMD 和 CUDA kernel 内部优化。**

## 测试环境与方法

- CPU：AMD Ryzen 7 9700X，8 核 16 线程；
- GPU：NVIDIA GeForce RTX 5070 Ti 16 GiB，compute capability 12.0；
- 内存：32 GiB；
- 编译器：GCC 13.3、NVCC 13.0；
- 构建：CMake Release + IPO/LTO，CPU `auto` 在本机选择 AVX2；
- CPU 归因：Valgrind Callgrind；
- CUDA 时间线：Nsight Systems 2025.3；
- CUDA 资源：`cuobjdump`；
- 同步系统调用：`strace -f -c`。

常规吞吐取预热后连续五次运行的中位数。CPU 显式使用 AVX2，CUDA 数据来自单次 CLI 搜索，
包含 CUDA runtime 和设备初始化。冷 CLI CUDA 数字不能与同一进程内已经初始化的暖运行
数字混用。

本机 `perf_event_paranoid=4`，不能采集硬件 PMU；Nsight Compute 也因
`ERR_NVGPUCTRPERM` 无法读取 GPU 性能计数器。因此本文 CPU 百分比是 **Callgrind 动态指令
占比**，不是严格的 wall-clock 占比；CUDA 数据可以说明 API、kernel 和拷贝的时间线，不能
据此断言 SM occupancy、cache miss 或 DRAM 带宽已经饱和。

## 端到端基线

| 阈值 | 输入范围与候选数 | CPU 1线程 | CPU 8线程 | CPU 16线程 | CUDA 单次 CLI |
|---:|---:|---:|---:|---:|---:|
| 45 | range 10000，4亿 | 约 0.382 G/s | 约 2.76 G/s | 约 4.05 G/s | 约 2.62 G/s |
| 35 | range 5000，1亿 | 约 0.212 G/s | 未采集 | 约 1.53 G/s | 约 0.780 G/s |
| 20 | range 3000，3600万 | 约 0.0707 G/s | 约 0.424 G/s | 约 0.466 G/s | 约 0.251 G/s |

这张表不能简化成“CPU 永远快于 CUDA”。当前 CUDA 单次 CLI 被约 0.11--0.19 秒的固定
成本主导；同一进程暖运行的吞吐更高。它说明的是：在当前生命周期和同步模型下，即使输入
达到 4 亿候选，GPU 算力仍未有效转化为端到端优势。

阈值之间也不能直接横向视作硬件能力。阈值 45 命中稀疏；阈值 20 的 3600 万候选产生
`16,461,623` 条结果，计数、排队、复制和回调都是搜索契约要求的真实工作。

## CPU 热点

### 高阈值：位图与滑动方框各占约一半

阈值 45、单线程 AVX2 的 Callgrind 指令归因：

| 区域 | 动态指令占比 |
|---|---:|
| `build_map_avx2()` | 约 47.0% |
| worker 与高阈值滑动方框路径 | 约 51.5% |
| 其他 | 约 1.5% |

位图内部，LCG 与 `nextInt(10)` 叶子操作合计约 30.5%：48 位 state 乘加与掩码约
11.7%，右移取 bits 约 4.7%，limit 判断与常数 `% 10` 约 14.1%。编译器已经把常数取模
降成乘法和移位，继续手写 `% 10` magic constant 不会改变热点层级。

当前 AVX2 只批量生成每 tile 约 512 个 `xterm`，随后约 26.2 万次 LCG 判定仍为标量。
对应代码位于 `src/backends/avx2.cpp` 和 `src/core/domain.hpp`。稳定大范围测试中 AVX2 相对
scalar 仅快约 6.3%，与其极小的向量化覆盖面一致。

完整 AVX2/NEON LCG 仍是有效方向，但必须同时覆盖 48 位乘加、bits 提取和整除判定，并把
极罕见的 rejection lane 精确转入标量冷路径。它最多只解决高阈值中的部分位图成本，不能
替代对其他阈值管线的优化。

### 中阈值：SAT 查询而非 SAT 构建主导

阈值 35 的指令归因：

| 区域 | 动态指令占比 |
|---|---:|
| AVX2 位图生成 | 约 18.3% |
| SAT 构建与候选扫描 | 约 81.2% |
| 其中 SAT 构建 | 约 7% |

主要成本不是生成积分图，而是通过方框预筛后的候选执行 20 次 `rectangle_sum()`。每次查询
包含四处 SAT 读取及相应地址计算，相邻中心之间的高度重叠没有转化成批量计算。热点位于
`src/engine/search.cpp` 的 `scan_tile_sat()`。

此前尝试过重排 run 并逐候选 early-exit，但额外分支和控制依赖造成了端到端回退，修改已
撤销。除非新的实现能够批量处理多个中心、用无分支上界或用实测证明收益，不应再次引入
同类逐候选分支链。

### 低阈值：滑动边界与结果交付共同限制

阈值 20 的指令归因：

| 区域 | 动态指令占比 |
|---|---:|
| 20段滑动边界更新 | 约 53.1% |
| run 循环与地址计算 | 约 12.9% |
| 位图生成 | 约 5.6% |
| 结果 append | 约 3.5% |

剩余成本还包括批次交换、队列同步和调用线程消费。线程扩展也印证了这一点：

| 线程数 | 吞吐 | 相对单线程 |
|---:|---:|---:|
| 1 | 70.7 M/s | 1.00x |
| 8 | 424 M/s | 6.00x |
| 16 | 466 M/s | 6.59x |

8 到 16 线程只提升约 9.9%。相同 16 线程环境中，阈值 20、3600 万候选产生约 52,343 次
`futex` 调用，而阈值 45、4 亿候选只有 41 次。CLI 默认每批 1024 条结果，密集命中时多个
worker 很快填满深度为 2 的有界队列，并在条件变量上等待调用线程。

因此低阈值优化必须保留以下约束：回调仍由调用 `ss_search()` 的线程串行触发；内存仍有界；
慢消费者仍形成背压；成功状态不能漏掉或截断结果。单纯扩大为无界队列或只统计不回传，
都不是正常搜索路径的有效优化。

## CUDA 热点

### 高阈值：GPU 计算很短，主机逐 tile 串行

阈值 45、4 亿候选共切分为 1681 个 tile。当前每 tile 启动两个 kernel，并在读取结果前执行
一次 `cudaDeviceSynchronize()`，合计 3362 次 kernel launch 和 1681 次设备级同步。

Nsight Systems 汇总如下：

| GPU/API 区域 | 总时间 | 说明 |
|---|---:|---|
| `count_donut_prefix` kernel | 约 11.42 ms | kernel 时间的约 63% |
| `build_fused_prefix` kernel | 约 6.72 ms | kernel 时间的约 37% |
| 两个 kernel 合计 | 约 18.14 ms | 纯 GPU kernel 时间 |
| `cudaDeviceSynchronize` API | 约 22.52 ms | 1681 次 |
| `cudaMemcpy` API | 约 8.35 ms | count 与结果回传 |
| kernel launch API | 约 6.76 ms | 3362 次 |
| `cudaMemset` API | 约 2.09 ms | 每 tile 清零计数 |

当前 `search_cuda()` 还会在每次调用中执行设备探测、`cudaSetDevice()`、三次 `cudaMalloc()`、
一次 `cudaMallocHost()`、常量上传和对应释放。小范围搜索也需要约 0.11--0.19 秒；候选数从
3600 万增加到 4 亿时，部分运行只增加约 29 ms。这是固定初始化和串行编排主导的典型特征。

代码落点是 `src/backends/cuda.cu` 的 tile 双循环。第一优先级应消除循环内部的设备级同步，
让多个 tile 和主机回传形成流水，而不是先优化仅有约 18 ms 的 kernel。

### 低阈值：结果传输和主机重打包超过 kernel

阈值 20、3600 万候选共 169 个 tile，产生 `16,461,623` 条结果：

| 区域 | 测量值 |
|---|---:|
| kernel 总时间 | 约 1.94 ms |
| D2H 数据量 | 约 197.54 MB |
| D2H GPU 时间 | 约 7.40 ms |
| `cudaMemcpy` API 时间 | 约 9.48 ms |

回传后，主机还要逐条遍历锁页缓冲并重新打包成 ABI 回调批次。这里的瓶颈不是可以通过一个
更快的计数 kernel 消除的；设计多 tile 异步流水时，必须为密集结果保留 D2H 带宽、主机
消费和背压预算。

### 架构目标：必要的构建卫生，不是当前 P0

普通本地构建缓存曾以 `sm_75` 为目标，而 RTX 5070 Ti 原生目标是 `sm_120`。`cuobjdump`
显示资源差异：

| kernel | `sm_75` 寄存器 | `sm_120` 寄存器 |
|---|---:|---:|
| 圆环计数 | 70 | 42 |
| 位图与行前缀 | 13 | 16 |

原生 `sm_120` 使圆环 kernel 约快 17.6%、kernel 总时间约快 11.4%，但端到端只改善约
0--3%。Release 和发布构建应显式选择合理的 CUDA architecture 或提供兼容的 fat binary，
但它不是当前首要性能工作；主机生命周期优化完成后应重新测量其实际影响。

## 下一阶段实施路线

### P0：CUDA 生命周期与多 tile 异步流水线

1. 缓存已初始化的 device/context、圆环常量、设备缓冲和锁页主机缓冲，避免每次搜索重复
   初始化和分配；使用受控资源池或每调用 slot 保证并发 `ss_search()` 的线程安全。
2. 一次提交多个 tile，移除 tile 内的 `cudaDeviceSynchronize()`；用 stream 和 event 表达
   build、count、D2H 与复用依赖。
3. 至少采用双缓冲：GPU 计算下一批 tile 时，上一批 count/results 异步回传并由调用线程
   消费。不要让默认 CPU `auto` 为此初始化 CUDA。
4. 结果容量按批次严格证明。密集结果超过当前缓冲预算时必须拆批、扩容或返回明确错误，
   不能 clamp 后成功返回；设备与主机内存都必须保持有界。
5. 基准增加 CUDA cold、warm、kernel、D2H、主机回调五类时间，并用 NVTX 标注初始化、
   提交、等待、回传和消费阶段。

这一阶段的验收指标不是某个 kernel 快多少，而是暖搜索中固定初始化接近消失、同步次数从
每 tile 一次降到每批/event 一次，并且大范围高阈值端到端吞吐显著高于当前基线。

### P1：低阈值 CPU 与有界结果交付

1. 同时处理多个相邻中心，把 20 段左右边界的加减改成批量、可向量化的数据流，减少 run
   循环和重复地址计算。
2. 将固定 1024 条批次改成受上限约束的自适应策略，可按命中率和字节预算调整；同时调节
   队列深度，目标是减少 `futex`，而不是解除背压。
3. 复用批次存储，减少 `vector` move 后重新 reserve、分配和主机侧重打包；保持所有用户
   回调仍在调用线程串行发生。
4. 基准增加“仅算法计数”的诊断模式以分离计数成本和强制结果交付成本，但普通搜索 API
   语义不变，正式吞吐仍报告完整交付路径。

### P2：中阈值 SAT 与圆环查询

1. 原型验证 bit-packed map、固定圆环 mask 和 `popcount`，与当前 byte map + SAT 在阈值
   31--40 逐点比较。
2. 一次计算多个相邻中心，复用 SAT 地址或打包位图加载，让编译器能够向量化；避免每候选
   串行执行 20 组四点查询。
3. 使用实际方框通过率重新校准 30/31 和 40/41 策略边界，必要时按 tile 采样选择，但选择
   逻辑不能改变结果。
4. 不重复引入已证实回退的 branch-heavy run early-exit，除非新的批量实现提供同机数据。

### P3：完整 CPU SIMD 与 kernel 内部优化

1. 实现完整 AVX2/NEON LCG、limit 和模 10 判定，以标量 lane fallback 精确处理 rejection；
   只有逐位一致且端到端至少达到现有 `auto` 收益门槛时才参与自动分派。
2. 可增加独立 AVX-512 算子，但不得启用全局 `-march=native`，不得修改已有公共枚举数值。
3. CUDA 位图前缀 kernel 可研究 warp/block scan，减少当前 9 轮共享内存 Hillis--Steele scan。
4. 只有 P0 完成、kernel 已成为暖搜索的显著占比后，才评估 kernel 融合、寄存器压力和布局
   微调；届时需要 Nsight Compute 权限支持结论。

## 当前不优先处理

- 继续从代数上消除 LCG 或 `chunkSeed ^ A`：XOR 与整数乘法进位不在同一代数结构，现有
  单次 48 位乘加已经足够紧凑；
- 跨 tile 复用约 6.56% 的重叠位图：收益只覆盖位图阶段，却会增加调度和所有权复杂度；
- 让 `SS_BACKEND_AUTO` 探测并初始化 GPU：会伤害 CLI 启动、小范围搜索和无 GPU 环境；
- 恢复旧的逐 run early-exit：现有实测为负收益；
- 通过固定结果上限、静默截断、无界缓存或弱化 rejection sampling 换取吞吐。

## 正确性与性能验收

每批优化必须先满足正确性，再判断性能：

1. scalar、AVX2、NEON 与可用 CUDA 后端逐项差分，覆盖阈值
   `0/30/31/40/41/45/192`；
2. 覆盖空区域、负坐标、tile 边界和密集命中，并专门验证任何批次容量下都不截断；
3. 覆盖取消、结果回调终止、进度，以及回调只由调用线程串行触发的契约；
4. 运行 Release 全部 CTest、`full_golden_regression`、`c_api_smoke` 和搜索后端契约测试；
5. 性能使用同机交替运行至少五次的中位数，CPU 至少报告 1/8/16 线程以及低、中、高阈值；
6. CUDA 分开报告 cold、warm、kernel、D2H 和主机回调时间，并记录 tile/launch/sync 数量；
7. 验证 host/device 内存有明确上限，生产者快于消费者时仍有正确背压；
8. CI 不加入跨机器绝对耗时断言，只检查正确性、构建目标和可选后端契约。

完成 P0 后必须重新采样 CUDA 时间线，再决定 P3 中 kernel 优化的先后；完成 P1 后也应重新
测量低阈值的 `futex` 数与 8 到 16 线程扩展。优化路线以新的端到端证据迭代，不把本次热点
比例固化为长期架构假设。
